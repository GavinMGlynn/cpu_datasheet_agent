Building an agent, and the MCP server it works through

A tour of this repository for someone who knows Node and React and has used Claude, but has not built an agent or written an MCP server. Everything here is code you can open: file paths are real, and every command runs.

1What an agent is here

An agent, in this project, is four things and nothing else: a prompt file, a set of tools, a harness that runs the model in a loop, and a record of everything that happened. There is no framework, no planner, no chain abstraction. The interesting part is not the loop — the SDK owns that — it is what the loop is allowed to touch.

The project keeps two layers strictly apart. The deterministic layer fetches, caches and stores; it has no judgement in it. The agent layer does the one genuinely hard thing: reading parameters out of a datasheet PDF and reconciling them against what distributors publish. A tool is how the second reaches the first, and it is the only way it can.

Four rules that make a run reproducible

Rule Where it lives Why
The prompt is a versioned file, never an edited string prompts/extract.v1.md Its SHA-256 is stored with the run, so "extract.v1" means one thing for ever.
No built-in tools, no settings files tools: [], settingSources: [] Otherwise the same prompt means different things on two machines.
Every tool call is recorded before it runs and after it ends src/log (the ledger) This is the eval dataset. It cannot be reconstructed afterwards.
Money is gated three ways registry · hook · harness An agent with a credit card needs more than good intentions.

3Tools: writing one

A tool is a name, a description the model reads, an input schema, an output schema, a handler, and two flags. That is the entire contract. Here is a real one, trimmed:

Four things are worth dwelling on, because they are what make the surface safe.

The description is a prompt

The model chooses tools by reading descriptions. "Download a datasheet PDF" is an API doc; "one datasheet usually covers a whole family, so the part number given is linked to it rather than owning it" is a piece of domain knowledge that stops a whole class of wrong answer. Write descriptions for a capable colleague who has never seen your data model.

Strict schemas, both directions

z.strictObject means an unrecognised key is an error, not something quietly dropped. The registry parses the input before the handler sees it and parses the handler's own output afterwards — a handler that breaks its own contract raises TOOL_OUTPUT_INVALID, which is a different fault from the caller sending nonsense and is worth telling apart.

spendsQuota is the money flag

A tool that can cost real money — a distributor API call — says so. The declaration is what the first money gate reads, and what the hook reads, and what the ledger records. Downloading a manufacturer's PDF is free, so fetch_datasheet is not gated; fetch_offers is.

Annotations are hints to the client

readOnlyHint and destructiveHint travel over MCP so a client can decide what to confirm with a person. They are hints, not enforcement: the enforcement is the gate.

The pattern to steal: validate on the way in and on the way out, record both ends, and let a failure be a value the model can read rather than an exception that kills the run. A model that gets TOOL_NOT_FOUND: no datasheet with digest … has been fetched; call fetch_datasheet first will do the right thing next turn. One that gets a transport error can only guess.

4MCP: what it is, and what crosses the wire

The Model Context Protocol is a small JSON-RPC protocol for handing tools (and prompts, and resources) to a model. A server advertises tools with JSON Schema; a client — Claude Code, the MCP Inspector, your own harness — lists them and calls them. That is genuinely all it is. The value is that the same tool surface works for every client without being rewritten.

This project writes its tools once, in the registry, and adapts them twice:

Three things that actually cross the wire

What How it travels Why it matters
The tool list Name, description, JSON Schema for input (and output, when it is an object) Generated from the Zod schemas. A schema the client cannot convert empties the whole list, not just its own entry — that bug once cost a real run every tool it had.
Results JSON as text, plus structuredContent for object outputs; an image block for render_page A model that can see a mangled table is the reason that tool exists. Base64 inside a JSON string is not that.
Failures Error results carrying { name, code, message, details } The model reads the code and decides what to do. A transport failure tells it nothing and ends the session.

stdout belongs to the protocol. An stdio MCP server speaks JSON-RPC on stdout. One stray console.log corrupts the session — not "looks untidy", corrupts. Every log line in this project goes to stderr, and a test asserts a full session writes nothing to stdout.

Run it yourself

Start the server (it talks JSON-RPC on stdin/stdout, so it will look like it hangs): 

npx tsx bin/chip-mcp.ts

Point Claude Code at it by putting this in .mcp.json at the repo root: 

{
  "mcpServers": {
    "chip": {
      "command": "npx",
      "args": ["tsx", "bin/chip-mcp.ts"],
      "env": { "DATA_DIR": "./data" }
    }
  }
}

Then ask Claude Code something like "use the chip tools to show me what is stored for TPS54331DR". The tools appear as mcp__chip__get_part and friends.

5The harness, and the one line that makes it testable

@anthropic-ai/claude-agent-sdk gives you query({ prompt, options }), an async iterable of messages. You consume it to the end; the SDK runs the model, calls tools, feeds results back, and stops when the model is done or a limit is hit. The run's own code is a for await loop and a handful of bookkeeping.

Note deps.query, not the imported query. That one indirection is what makes an agent testable at all:

In production the runner gets SDK_QUERY. In a test it gets a generator that yields a scripted conversation — including tool calls, which really do run against a temporary database. Every branch of a run (a model that gave up, a harness that threw, a part stored cleanly, an escalation raised) is then an ordinary unit test with no network and no API key.

6The money gates

This agent can spend real money: distributor APIs have quotas, and the model itself costs per token. One check is not enough, because each one protects against a different thing going wrong.

What the hook decides

Why letting a cache-only call through matters. The obvious design — deny every spending tool in a no-spend run — stops the run from reading data you have already paid for. Being able to rerun a part for free is the entire point of the cache, so the gate allows the call and lets the miss be the refusal.

7Reading a run back

When the loop ends, nothing about the run is taken on trust. What it achieved is read back out of the ledger and the database — not from what the model said it did.

  • The ledger (data/ledger/YYYY-MM-DD.jsonl) has one line per tool call: the session, the tool, the input, the output or the error, the duration, whether it could spend, and the id of the call it hangs under. Every gate decision is a line too.
  • The run row (SQLite) records turns, cost, how it ended, how many tools failed, how many spends were refused, how many cache misses there were, and whether a part was actually stored.
  • The part is the only thing that counts as output, and it is rejected rather than repaired if any value is the wrong shape or lacks a page number.

Look at what a run did, without leaving the terminal:

# the last runs, newest first
sqlite3 data/chip.sqlite \
  "select mpn, kind, result, turns, round(cost_usd,2) from runs order by started_at desc limit 5;"

# every tool call of the most recent session
tail -n 50 data/ledger/*.jsonl | jq -r '[.tool, .durationMs, (.error.code // "ok")] | @tsv'

Or open the site, which is the same data with charts on it: npm run web.

8The verification pass, and why it gets a fresh context

Extraction is optimistic by nature: the model that read a number is the worst possible judge of whether it read it correctly. So a second run, with a different prompt and no memory of the first, takes each stored value and checks it against the page it claims to come from. 

npx tsx bin/chip-run.ts verify TPS54331DR

9Testing an agent

"You can't test an agent, it's non-deterministic" is half true and usually used as an excuse. Split the claim in two and both halves become testable.

The plumbing is deterministic — test it like any other code

Tools, schemas, the gate, the ledger, the run bookkeeping, the conclusion logic: all of it is ordinary TypeScript with no model in it. This repository holds it to 100% lines, branches and functions, per file. The scripted QueryFn from §5 is what lets a run's own branches be covered without a single API call.

The model's judgement is measured, not asserted

You cannot assert that a model read a table correctly. You can measure how often it does, against parts a person has read by hand. That is the golden set (eval/golden/) and the evaluation harness: 

npx tsx bin/chip-eval.ts run                       # scores every golden part
npx tsx bin/chip-eval.ts compare eval/results/<a> eval/results/<b>

The first baseline — extract.v1 on claude-opus-5, 22 parts — scored 90.6% recall, 90.6% precision and 59.3% of citations on the exact page, for $87.24. That last number is the one worth staring at: it is why the prompt is versioned and why a rerun has to be free.

Layer What it proves Costs money?
Unit tests Every branch of every tool and of the runner No
Behaviour tests What an endpoint or a run does, not how No
Integration A real database, a real ledger, a real PDF through poppler No
Live contract tests That a distributor's API still answers the way the adapter believes Opt-in
Evaluation How well the model does, as a number you can compare Yes — deliberately

10Add your own tool, end to end

Say you want a tool that reports the cheapest stored part in a category. The whole job:

Step File What you write
1 · Define it src/tools/definitions/query-tools.ts defineTool({ name, description, input, output, spendsQuota, annotations, handler })
2 · Register it src/tools/definitions/index.ts Add it to buildRegistry(). Duplicate names are refused.
3 · Test it …/query-tools.test.ts Call it through registry.call() so the schemas and the ledger are in the test too.
4 · Tell the model about it prompts/extract.v2.md A new prompt version if a run should use it. Never edit v1.
5 · Nothing else — Both MCP adapters pick it up automatically; the site's health page lists it; the ledger records it.

Checklist for the definition itself:

  • Does the description say the domain thing a newcomer would get wrong?
  • Is the input a strictObject, so a typo is refused rather than ignored?
  • Can the output represent "I could not find it" without lying? (null with provenance is a fact; an invented number is not.)
  • Does it spend money? Then spendsQuota: true and accept confirmSpend.
  • Are failures thrown as errors with codes the model can read and act on?

11Gotchas worth knowing before you start

A schema the client cannot serialise empties the whole tool list

A Zod record in one tool's input once made the bundled SDK drop every tool. The server reported itself connected, the model was handed nothing, and it started writing tool calls as prose. Prefer arrays of { key, value } pairs to open-ended records, and have a test that lists the tools over a real connection.

Context is the expensive part, not the tokens you think

One page of datasheet text costs about a dollar to hold in context across a run. The single biggest cost saving in this project was not a cheaper model — it was not writing the whole parameter set out twice.

Nobody is watching, so "ask" must not mean "wait"

A headless run cannot block on a person. ask_human records the question, marks the part, and the run carries on. The site has a queue of those questions; an answer is recorded there later, with who answered it and why.

Let the model see the page

Dense electrical-characteristics tables mangle badly through text extraction. read_pages returns shape metrics with each page; when they say the columns have collapsed, the prompt tells the model to call render_page and read the image instead — and to record method: "image" so the verification pass knows how the number was read.

Record before you act, not after

The ledger writes a line when a call begins and completes it when it ends. A crash in the middle leaves evidence. A log written after the fact does not.
