Datasheet Agent Architecture

Given a part number, produce a record a hardware engineer can trust: parameters, where each one came from, what it costs, and how it is categorised. This is how the pieces fit, and why the boundaries sit where they do.

01 The problem shapes the design

Two properties of this domain drive every decision below. Neither is incidental.

A datasheet is a rendering, not a database. Values live in tables that lose their structure when extracted as text. One datasheet usually covers a whole family of part numbers, and the suffix that separates them (TPS54331D from TPS54331DR) encodes packaging and temperature grade rather than anything electrical.

A wrong answer is worse than no answer. A misread absolute maximum input voltage does not produce a slightly worse recommendation. It produces a dead board.

So every value carries where it came from, nothing is coerced into fitting, and anything ambiguous stops and asks.

02 Two layers, one crossing point

The system is split in half, and the split is enforced by module boundaries rather than by convention. The deterministic half fetches, parses, converts and stores; given the same inputs it produces the same outputs every time, with no model in the loop. The agent half does the one thing that genuinely needs judgement: reading a page and deciding what the numbers mean.

03 What happens to one part

Each stage is a separate tool call, so each is individually cached, logged and re-runnable. Only two stages involve a model.

Three that carry more weight than their size suggests

Page metrics. Alongside a page's text, the PDF toolkit returns line counts, columns detected by whitespace runs, and how many lines hold numbers with no label. Those numbers exist so the agent can decide to render a page as an image without exercising judgement about it, which keeps a judgement call out of the deterministic layer.

Numeric bounds in columns. Parameters are stored as JSON and with their bounds extracted into columns. That is what makes the end goal a SQL filter rather than a scan: every part whose input range covers 8 V–36 V at 2 A.

The budget counter. Nexar's evaluation tier allows 100 parts for the lifetime of the account. Every operation reserves from a persisted counter inside an immediate transaction before any network call, so the limit cannot be exceeded even by a bug.

05 How the pieces interact

The cache is the only door to the network

Provenance travels with the value, not beside it

A parameter is never a bare number anywhere in the system. It is a { value, provenance, confidence } triple from the moment it is created, through reconciliation, into the database and out again. There is no stage at which a value exists without knowing where it came from, because there is no type for that.

Escalation is an outcome, not a failure

ask_human writes an escalation and returns; it never blocks. The part is marked as needing a person and the run ends cleanly. A run that escalates has succeeded at its actual job, which is to avoid asserting something it cannot support.

On disk

None of it is committed. .env holds credentials and is gitignored; the config loader is the only thing that reads it, and the redactor keeps its values out of both the logs and the ledger.

06 Rules, and what enforces them

Four rules govern the project. Each has a mechanism rather than an intention, because an intention is not reviewable.

Non-negotiables
RuleMechanism
Every parameter carries provenance No schema exists for a datasheet value without a page number
Validate and reject, never coerce upsertPart parses the whole aggregate before it writes
Escalate, don't guess A parameter in conflict makes verified status unrepresentable
Log every tool call withLedger wraps registration, not call sites

Three engineering standards sit alongside them: a module is finished completely before the next begins, coverage is 100% per file with the build failing otherwise, and no tool in the pipeline may emit a warning.

07 Deferred, deliberately

Hosting is designed for and not built: Fargate for the runner, S3 behind CacheStore, Secrets Manager in place of .env, a queue for work, and Postgres behind the same repository interfaces. Each is a swap at a seam that already exists, which is the point of the seams. None of it happens until the system runs reliably on one machine.
